对照与洞察

这一轮能证明的不是“谁覆盖得多”，而是“block”在不同产品里根本不是同一个计量单位。任何跨源总数，在补齐 unit、grain、是否本轮核实之前都不可读。

本页只对照各家如何定义、按什么粒度计数、query 到来时是选目录还是运行时组合。它不给出“我们需要 N 个 blocks”，也不使用尚未复算的 56 条 draft query 做覆盖结论。

粒度标尺

把各源放到同一套层级上：原语、区域、整页、模板、运行时组合。一个源可以同时落在多层。这张图要说明的是：跨层数字不能比较，更不能加总。

基线 HOS7 用钴蓝浅底标出。生成式来源用虚线，表示它们往往没有传统 block 目录。位置来自各源官方粒度，不是按数量排序。

来源对照

不是排行榜。每张卡片给出官方数字、单位、粒度和本轮是否核实。点开可看分类、场景、组件族和官方链接。

69 对 69 是巧合，不是同类。 HOS7 的 69 是混粒度 blocks；CopilotKit 的 69 是 standard catalog 组件。两个数字相同，对象、粒度、响应模型都不同，禁止并列成同一量纲。

Query 如何变成界面

灵活性并不自动来自目录变大。有的源从目录里挑选，有的把区域组合起来，有的在运行时生成，有的把提示写成代码。同一源可以走不止一条路。

生成式 UI 的灵活性来自运行时组合，不来自目录规模。OpenUI 甚至要求限制 library size：组件越多，提示词与选择噪声越大。

场景簇

簇可以组织导航，不能跨源加总。 同一簇里，各源的最小可安装单位并不相同。营销簇被变体撑大；后台深度分化很大；agent-chat 几乎不是目录问题；HOS7 是移动内容消费，不是营销或电商。

这些簇是本轮的分析映射，不是任何一家的官方 taxonomy。下沉到 section 类型时，分类法就开始各说各话。

组件族

大目录不等于深应用。 例如 Shadcnblocks 的 Gantt 为 1、Kanban 为 3，而 ReUI 的 Data Grid 组为 61、Gantt 为 4、Kanban Board 为 10。这张表用来辨认框架族、深度族和运行时族，不是 HOS7 的采购清单。

移动族（tab-bar、search-field、sheet、mini-player 等）是 HOS7 特有的依赖，桌面商业目录基本不把它当作 block 家族，因此不在这张跨源表里加总。导航族同名不同形态（移动底栏 vs 桌面顶栏），本轮对照没有单独成行。

叠回 HOS7

69 不能读成一个平面目录。资产重心在「区域 × data-props」的 53 个；14 个 page-type 全部是 baked demo，却正是 ds.py route 当前选择的入口。先重标，不在这一步扩编。

已成立的洞察

下列条目本轮可以成立。假设与未核实的数字不写在这里。

该学，与不该学

反哺我们自己的目录：学层级、学 frame 与数据契约，不学变体库存，也不把“做多少个”当作这一步的结论。

该学

  1. 把层级做成一等字段 每个条目回答 grain（primitive / region / page / template）、kind（component / demo）、data_contract、scene、routeable。防止再把卡片、区域、整页塞进同一个 69。
  2. 把 block 当作可安装的 frame ReUI 写：“Treat a block as the frame. Bring your own tokens, copy, and data instead of shipping the sample content.” 21st 也要求把组件逻辑与 demo 内容分开。demo 是 frame 的展示态，不是另一类资产。route 应只选 routeable 且 data_contract 不为空的 frame。
  3. 按产品表面分组，而不是平铺上百个 section 类型 检索先缩小场景，再选条目，降低 OpenUI 所说的“组件越多越困惑”。HOS7 更适合停在 home / search / settings / media / profile / onboarding 这类表面。
  4. 先重标，不扩编 给 69 条补字段；把 big-image-card 这类卡片单元从含混的 region 里标清；14 个 page-type 标为 demo_only。若以后新增，优先补 data-driven 的 page frame，而不是再补一个 demo 整页。

不该学

  1. 不要把变体库存当成覆盖目标 Shadcnblocks 的 2,866 里，Hero 292、Feature 334 是视觉变体；Gantt 1、Kanban 3、Onboarding 2 才暴露真实深度。把 2,866 当目标，会得到同质 hero，而不是更强的产品覆盖。
  2. 不要学对不上的双口径 Aceternity 首页写 183+，All-Access 文案写 182。对外报数必须能指向一个可复算的 registry 或索引。
  3. 不要把混合库存写成 blocks 21st 的 12,000+ 明确包含 components、templates、themes。Kibo 的 1,101 patterns 也不得画成 1,101 个 blocks。
  4. 不要假设大目录等于更强的 agent 能力 CopilotKit 与 OpenUI 的能力来自运行时与协议。对 agent 更重要的是可检索的场景、清晰的数据契约，以及少而准的 frame。
  5. 不要为 69 条硬造 133 类平铺 taxonomy 那是商业浏览器的信息架构，不是 agent 的选择架构。
